# 模型管理：上传与存储逻辑说明

本文详细说明「模型管理」中**上传模型**的完整逻辑：文件如何存入 MinIO、如何在 MongoDB 中生成/更新记录，以及非 GLB 格式的转换流程。

---

## 一、整体结论（你的理解）

- **上传的模型文件** → 保存在 **MinIO**（对象存储）
- **每条上传** → 在 **MongoDB 的 `files` 集合**里生成**一条记录**（元数据，含 `file_path` 等）
- **转换后的 GLB** → 存入 MinIO 的**转换桶**，并在同一条 `files` 记录中更新 `conversion` 字段

---

## 二、涉及的核心位置

| 存储/逻辑 | 位置 |
|-----------|------|
| MinIO 桶名 | `app/core/minio_client.py`：`SOURCE_BUCKET_NAME`、`CONVERTED_BUCKET_NAME` |
| 上传接口 | `app/routers/files.py`：`POST /files/upload` |
| MongoDB 集合 | `db.files`（文件元数据）、`db.metadata`（产品结构元数据，由转换任务写入） |
| 转换任务 | `app/tasks/file_converter.py`、`app/tasks/task_manager.py` |

## 三、上传接口逻辑（POST /files/upload）

**文件**：`app/routers/files.py` 约 69–162 行。

### 3.1 入参与校验

- **file**：上传的 3D 模型文件（必填）
- **metadata**：JSON 字符串，可选，会合并进最终存库的元数据
- **current_user**：依赖注入，未登录 401

扩展名必须在 `file_formats.json` 给出的支持列表中，否则 400。

### 3.2 生成存储路径

```python
file_data = await file.read()
file_path = f"{current_user.id}/{datetime.now().strftime('%Y%m%d_%H%M%S')}_{file.filename}"
```

- 格式：`{user_id}/{YYYYMMDD_HHMMSS}_{原始文件名}`
- 该路径同时用于 MinIO 对象名和 MongoDB 中的 `file_path` 字段

### 3.3 分支一：扩展名为 GLB

- 先上传到 **转换桶** `CONVERTED_BUCKET_NAME`（`converted-files`）
- 再上传到 **源文件桶** `SOURCE_BUCKET_NAME`（`sourece-files`）
- 不创建异步转换任务，直接构造 `conversion` 为「已完成」：
  - `status=COMPLETED`
  - `input_format=GLB`, `output_format=GLB`
  - `input_file_path`、`output_file_path` 均为上面的 `file_path`
  - `progress=100`，无 `task_id`

### 3.4 分支二：非 GLB（如 STEP、OBJ、FBX 等）

- 只上传到 **源文件桶** `SOURCE_BUCKET_NAME`
- `conversion` 为 `None`（不写 conversion 或后续由转换任务写入）


两个桶分别做什么
源文件桶（SOURCE_BUCKET_NAME）
存用户上传的原始文件，不改内容、不删，方便溯源和重新处理。
不管什么格式（.glb、.zip、.gltf 等），都会存一份到这里。
转换桶（CONVERTED_BUCKET_NAME）
可以理解为「待处理 / 转换工作区」：
需要转换的格式：先放这里，转换任务从这里读、结果也常写回这里（或再拷到别处）。
已经是 .glb 的：也拷一份到这里，这样所有“可被加载的成品”都从同一个桶取，流程统一（前端/加载逻辑只认转换桶的路径即可）。
隔离带来的好处
职责分开：原始文件不动，转换/加工只在转换桶或后续流程里做。
权限/策略好配：例如源文件桶长期保留，转换桶可以设短保留期或只放“当前在用”的成品。
流程统一：加载模型时只关心“转换桶里的 path”，不用再区分是“刚上传的 glb”还是“转换后的 glb”。
一句话
是的：不管什么格式，上传时都会进两个桶——源文件桶留底，转换桶做“待处理/成品”区，实现原始文件和可用的成品隔离、流程统一。

### 3.5 写 MongoDB（files 集合）

```python
metadata_dict = json.loads(metadata) if metadata else {}
metadata_dict.update({
    "filename": file.filename,
    "file_path": file_path,           # MinIO 中的路径
    "upload_date": datetime.now(),
    "file_size": len(file_data),
    "user_id": current_user.id,
    "username": current_user.username,
    "is_public": False,
    "tags": []
})
if conversion:
    metadata_dict["conversion"] = conversion.model_dump()

result = await db.files.insert_one(metadata_dict)
metadata_dict["_id"] = result.inserted_id
return FileMetadata(**metadata_dict)
```

- 集合：**`db.files`**
- 每条上传对应 **一条新文档**，包含 `_id`、`file_path`、`filename`、`user_id`、`conversion` 等
- 前端/场景里用的「文件 ID」即该文档的 `_id`

## 四、MinIO 桶与用途

（定义在 `app/core/minio_client.py`）

| 桶名 | 常量 | 用途 |
|------|------|------|
| 源文件 | `SOURCE_BUCKET_NAME` = `sourece-files` | 用户上传的原始文件（含 GLB） |
| 转换后 | `CONVERTED_BUCKET_NAME` = `converted-files` | 转换得到的 GLB/GLTF 等，供场景加载 |

- 上传时：**所有格式**都会在源文件桶里有一份（路径 `file_path`）
- GLB 上传时：同一 `file_path` 还会在转换桶里存一份，供前端直接当「已转换」使用
- 非 GLB 转换后：转换任务把结果**只**写入转换桶，路径格式：`{user_id}/{时间}_{输出文件名}`

## 五、非 GLB 的转换流程（与 MongoDB 的配合）

### 5.1 用户触发转换

- 接口：`POST /files/{file_id}/convert`（`app/routers/files.py` 约 411–512 行）
- 从 `db.files` 根据 `file_id` 取出该条记录，得到 `file_path`（MinIO 源文件路径）
- 创建转换任务（TaskType.FILE_CONVERSION），并把任务的 `task_id` 等写入该文件的 `conversion` 字段（status=PENDING 等）

### 5.2 任务执行（file_converter.py）

- 从 MinIO **源文件桶** 按 `task.input_file_path` 下载到临时目录
- 调用本地转换程序，生成 GLB/GLTF 等
- 将**转换结果**上传到 MinIO **转换桶**，得到 `converted_file_path`
- 若转换程序产出 XML，则解析并写入 **`db.metadata`**（产品结构元数据，按 `file_id` 关联）

### 5.3 更新 files 记录（task_manager.py）

- 转换成功后，`_update_file_metadata(task, output_file_path)` 被调用
- 对**同一条** `db.files` 文档做 `update_one`，`$set` 新的 `conversion` 对象：
  - `status=COMPLETED`
  - `output_file_path=output_file_path`（转换桶中的路径）
  - `progress=100` 等

因此：**同一次上传始终对应同一条 `files` 记录**；先有上传（MinIO + insert_one），后有可选的转换（MinIO 转换桶 + update_one conversion）。

## 六、读取与下载时的逻辑

- **列表**：`GET /files/list` → 查 `db.files.find({"user_id": current_user.id})`，不访问 MinIO
- **单文件详情/下载**：`GET /files/{file_path}` 或 `GET /files/download/{file_id}`  
  - 先用 `file_id` 或 `file_path` 在 `db.files` 中查出一条记录  
  - 用该记录的 `file_path` 向 MinIO 源文件桶申请预签名 URL（或转换桶的 `conversion.output_file_path` 用于转换后文件）

---

## 七、删除逻辑（注意点）

- 接口：`DELETE /files/{file_id}`（约 219–240 行）
- 当前实现：**只删除 MongoDB 中的记录**：`await db.files.delete_one({"_id": ObjectId(file_id)})`
- **未删除 MinIO 中对应对象**，因此 MinIO 里会留下「孤儿」文件；若需彻底清理，需在此处根据 `file_info["file_path"]` 和 `conversion.output_file_path` 调用 `minio_client.remove_object`。

## 八、数据流小结

```
用户上传文件 (POST /files/upload)
  │
  ├─ 校验扩展名 (file_formats.json)
  ├─ 生成 file_path = {user_id}/{时间}_{文件名}
  │
  ├─ [GLB]  → MinIO: converted-files + sourece-files
  │           构造 conversion 已完成
  │
  └─ [非GLB] → MinIO: sourece-files
               conversion = None
  │
  └─ MongoDB: db.files.insert_one(metadata_dict)
              一条记录，含 file_path、conversion 等

（可选）用户请求转换 (POST /files/{file_id}/convert)
  │
  ├─ db.files 中该条记录更新 conversion: { status: PENDING, task_id }
  ├─ 异步任务：MinIO 取源文件 → 本地转换 → 结果上传到 converted-files
  ├─ 若有 XML → db.metadata 插入产品结构
  └─ db.files 更新 conversion: { status: COMPLETED, output_file_path }
```

---

## 九、和「元数据」集合的区别

- **db.files**：一条记录 = 一次上传的文件，存 `file_path`、`filename`、`user_id`、`conversion` 等；用于列表、下载、转换状态。
- **db.metadata**：存的是**产品结构/节点元数据**（如 `ProductOccurrenceMetadata`），由转换任务在解析 XML 时写入，按 `file_id` 关联到某条 `files` 记录；用于结构树、节点信息等，**不是**「上传时必写」的那条记录。

你的理解「上传的模型保存在 MinIO，并在 MongoDB 里生成一条记录」指的就是：**文件在 MinIO，对应一条 `db.files` 记录**；上面是这条逻辑的详细拆解。
